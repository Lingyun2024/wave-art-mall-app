## R2 金流 e2e：本地實測抓出 P0（00:45–00:55，commit 6deda0c，全本地）
- **手法**：裝 `@electric-sql/pglite`（WASM Postgres，純記憶體離線）→ 建最小 schema → 套 `backend/order_amount_guard.sql` → 跑情境。腳本 `tools/test_money_guard.mjs`，`npm run test:money`，已納 `npm run gates`（門禁現為六條）。
- **P0 發現**：v1 SQL 若上線，**商城結帳 100% 失敗**。原因＝結算掛在 `orders` 的 `DEFERRABLE INITIALLY DEFERRED` 約束觸發器；PostgREST 每次請求各自提交，checkout 先插 orders(:416) 後插 order_items(:451)，第一次提交時明細尚空 → 拋「沒有任何訂單項目」。
  - **教訓（可複用）**：DB 防線的單元情境（同一交易內插完）會全綠，只有模擬**真實時序**才測得到。**凡 Supabase trigger 都要加一條「兩次獨立提交」的測試。**
- **v2 改法**：orders BEFORE INSERT 商城單歸零／BEFORE UPDATE 由 order_items 重算（堵事後改價）／order_items AFTER I/U/D 重算父單（`TG_OP` 取 order_id，DELETE 時 NEW 為 NULL）／七七地赦單（identity_type 非空）維持人工金額。
- **兩個實作坑**：① orders 的 BEFORE UPDATE 若無條件歸零，會把 order_items 觸發器算好的金額又洗掉 → 必須按 `TG_OP` 分工（INSERT 歸零／UPDATE 重算）。② AFTER DELETE 觸發器裡 `NEW` 是 NULL，`NEW.order_id` 回傳 NULL 不報錯但靜默失效 → 用 `TG_OP='DELETE' THEN OLD.order_id`。
- **已知取捨**：移除「空單硬擋」（結帳失敗元凶），攻擊者可建 0 元 0 明細空單，但取不到商品；配套＝SQL 檔末尾空單查詢定期清理。
- 實測結果：七情境 11 項斷言全綠；e2e 40 項通過。
- **待族族執行（動線上）**：`backend/order_amount_guard.sql` v2 仍未上 Supabase（v1 也從未執行，故無災情）。
