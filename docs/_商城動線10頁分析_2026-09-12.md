## 一、結構總覽：這 10 頁其實是「3 條動線 + 2 個孤兒」

| 動線 | 頁面鏈 | 狀態 |
|---|---|---|
| ① 商城主線 | category → product-detail → cart → checkout →（**內嵌成功區塊，不跳頁**）→ order-history | ✅ 全通 |
| ② 七七地赦支線 | holiday-form → **order-confirm**（從 localStorage 讀 orderData） | ✅ 通，但 order-confirm **不是商城頁** |
| ③ 認證 | auth（登入／註冊／忘記密碼皆內嵌本頁處理） | ✅ 通 |
| 孤兒 A | **order-success.html** — 只被根目錄草稿 `_live_checkout.html` 引用 | ⚠️ 死頁 |
| 孤兒 B | **reset-password.html ＝ pwreset.html** — `diff` 逐字節 **100% 相同**，活代碼零引用 | ⚠️ 死頁 ×2 |

**關鍵釐清**：
- `checkout.html:485` 下單成功後**不跳 `order-success.html`**，而是顯示內嵌 `success-block`（註釋寫明「避免依賴可能被 CLI 漏傳的新檔案」）→ order-success 是舊方案殘留。
- `order-confirm.html` 只被 `holiday-form.html` 連入，讀 `localStorage('orderData')`（:141），與商城下單無關——**檔名極易誤導維護者**。
- `auth.html` 的忘記密碼走 Supabase 郵件 + 本頁內嵌「設定新密碼」表單（註釋 :129-133），reset-password / pwreset 兩份檔案應是舊方案殘留。

## 二、🔴 P0：訂單金額可在客戶端偽造（商業風險）

```js
// checkout.html:399-401 — 金額在前端計算
let totalAmount = 0;
totalAmount += (item.products?.price || 0) * item.quantity;

// checkout.html:421 — 直接插入
total_amount: totalAmount,
```

| 環節 | 現況 | 問題 |
|---|---|---|
| 前端計算 | `totalAmount` 由 JS 累加 | 可被改 |
| orders INSERT RLS | `WITH CHECK (auth.uid() = user_id)`（schema:355-356） | **只驗本人，不驗金額** |
| orders 表約束 | `total_amount DECIMAL(12,2) NOT NULL`（schema:232） | **無 CHECK（>= 0 / > 0）** |

**攻擊路徑**：任何註冊用戶在 Console 用 `supabaseClient.from('orders').insert({ user_id: 自己, total_amount: 1, ... })` 即可建立 1 元訂單，完全繞過 checkout 頁。

**建議修法**（最小改動）：DB 端 BEFORE INSERT/UPDATE trigger，依 `order_items` join `products.price` 重算 `total_amount`，不符即 `RAISE EXCEPTION`；另加 `CHECK (total_amount >= 0)`。

## 三、🔴 P0（需驗證）：本地 schema 與 checkout 欄位對不上

`backend/supabase-schema.sql` 定義 `subtotal DECIMAL(12,2) NOT NULL`（:228），但 checkout 的 insert **沒有傳 `subtotal`**（也沒傳 `order_number`，後者有 trigger `trg_generate_order_number` 自動生成 ✅）。

- 若線上 DB 與本地 schema 一致 → **每次商城下單都會失敗**（not-null violation）。
- 若線上實際允許 NULL / 有 default → 本地 schema 檔已漂移。

**待辦**：查線上 `information_schema.columns` 確認 `subtotal` 實際定義。此項無法從本地斷定，故標記「需驗證」。
