# ADR-0001 · 引入建置流程與機器品質門檻

- **狀態**：✅ 已決策 —— **採 B（只補檢查，不引入打包）**
- **日期**：2026-09-13（當日 07:35 拍板，brief 第 0 節 Q2②）
- **決策者**：族族
- **上游**：`docs/briefs/2026-09-13_網站重寫.md`（已凍結）
- **影響**：所有後續頁面寫法、CI 門禁、字型流程、部署方式

---

## 背景

規範第 5 節要求 PR 上掛 6 條門禁（lint / typecheck / unit test / 覆蓋率 / build / 依賴安全），並明定「紅燈不可合併」。

**這個專案現在一條都跑不了**，實測現況：

| 門禁 | 現況證據 |
|---|---|
| lint / format | 無 `.eslintrc`、無 `.prettierrc` |
| typecheck | 無 `tsconfig.json`，全站是 HTML 內嵌 JS |
| unit test | 無任何測試檔、無 test runner |
| 覆蓋率 | 無從計算 |
| build | `package.json` 只有一個依賴 `pg`；無 vite / webpack，頁面靠 Tailwind Play CDN |
| 依賴安全 | 無 `npm audit` 流程、無 CI |

**後果**：過去所有品質判斷都靠「讀檔 + 人工比對」（例如 09-12 那批修復），這種方式**無法在 PR 上自動擋錯**。若不先解決這一項，拆出 3 個 agent 並行改寫，產出的仍是一堆無法驗收的 HTML，只是把「亂」加速而已。

> 結論：**門檻必須先於多 Agent 存在**；否則評審角色沒有可依據的客觀標準，規範第 5 節的獨立評審會退化成另一個 AI 的意見。

---

## 選項

### A. 維持純靜態，不建門檻
- 做法：沿用四條指令都缺的現狀
- 代價：無法在 PR 擋錯；重寫後一模一樣的亂會再長回來
- 適用：這個站台準備廢棄、不再維護

### B. 只補檢查，不引入打包（**推薦起點**）
- 做法：`package.json` 加 5 條 script，用現成工具跑，頁面結構完全不動
- 具體工具：
  - `format`：prettier（含 HTML）
  - `lint`：prettier --check + html-validate（抓標籤未閉合、重複 id、缺失 alt）
  - `check:links`：自寫連結/資源檢查（可直接回收 09-12 用過的 `linkcheck.py` 邏輯）
  - `test:e2e`：Playwright smoke——33 頁 HTTP 200 + 關鍵元素存在 + 表單能送出
  - `build`：`exit 0` 佔位（現階段無需打包，但門禁位先佔住）
- 代價：無法做元件化與 tree-shaking；但能立刻擋住「斷鏈、孤兒頁、標籤壞掉、表單壞掉」這四類實際發生過的錯
- 適用：想先止血、又要保留可隨時上線的能力

### C. 引入 Vite 建置
- 做法：改成 Vite 多頁應用，Tailwind 改編譯版，頁面拆成元件
- 代價：**33 頁全部要動**、部署設定要改、短期無法上線；且 ADR-0002/0003 必須同時定案
- 適用：確定要長期持續開發、頁面還會大幅增加

## 決策

採 **B（只補檢查，不引入打包）**，2026-09-13 07:35 由族族拍板（brief 第 0 節 Q2②），同日五條門檻建成並全綠（基線 `docs/baseline-2026-09-13.md`）。

日後若頁面持續增長、需要元件化與 tree-shaking，可依本 ADR 的 C 案升級——升級時必須連動 ADR-0002／0003 重新決策，不可單獨執行。

## 連帶影響（決策後才展開）

- 選 B 或 C → 才有 `lint` 可掛進 PR，規範第 5 節的門禁才能生效
- 選 C → 必須先定 ADR-0002（MPA/SPA）與 ADR-0003（樣式策略），三者互相鎖死
- 選 A → 本專案不適用多 Agent 交接規範（無客觀驗收層，拆了只會更亂）
