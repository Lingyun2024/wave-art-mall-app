# WAVE ART MALL 會員登入與權限入口 · 全盤規劃 Brief

STATUS: FROZEN

規劃日期：2026-09-30
正式頁面：`https://wave-art-mall.vercel.app/pages/auth.html`

## 1. 規劃目的

`pages/auth.html` 不只是登入表單，而是全站會員、訂單、火星療癒、購物車與管理頁的共同身分入口。

本次目標是先完整定義帳號流程、頁面狀態、登入後導向、管理權限、安全邊界、手機體驗、錯誤處理與驗收方法，再分階段實作。未經 Brief 與設計確認，不直接大幅重寫正式登入頁。

## 2. 最終交付

- 單一且清楚的登入、註冊、Email 驗證、忘記密碼及重設密碼流程。
- 所有需要登入的頁面使用一致的守門與回跳方式。
- 一般會員與管理員的權限提示和導向一致。
- Supabase Auth、Database RLS、Storage Policy 與前端流程相符。
- 手機與桌面皆可清楚操作，錯誤訊息使用繁體中文。
- 建立可重複執行的 Auth 測試清單與發布前門禁。

## 4. 現況摘要

### 已有能力

- Email／密碼登入。
- Email／密碼註冊。
- 註冊驗證信。
- 補寄驗證信。
- 忘記密碼寄信。
- 在 `auth.html` 內設定新密碼。
- `requireLogin()` 可保存原本網址並導向登入頁。
- 登入成功後會嘗試回到原本頁面。
- 常見 Supabase 英文錯誤會轉成繁體中文。

### 主要缺口

1. `auth.html` 與 `reset-password.html` 同時存在兩套重設密碼流程。
2. 有些頁面使用 `localStorage` 回跳，有些頁面使用未被登入頁讀取的 `?redirect=`。
3. 未登入、未驗證、無管理權限的處理方式在不同頁面不一致。
4. 管理員 Email 分散硬編碼在前端與 SQL。
5. 線上 Supabase RLS／Storage Policy 是否與本機 SQL 一致尚未核對。
6. `profiles` 的公開讀取政策可能暴露姓名、電話等個資，需要優先核對。
7. Auth 頁同時包含多個表單，但缺少正式的頁面狀態模型與可存取性規則。
8. 驗證信與重設密碼回跳固定為正式網址，不利本機與 Preview 驗證。
9. 註冊註解與實際 Email 驗證要求互相矛盾，容易讓後續維護者判斷錯誤。
10. 密碼最低僅 6 字元，沒有強度提示、顯示／隱藏密碼或 Caps Lock 提醒。

## 5. 使用者與權限角色

| 角色 | 可做事項 | 不可做事項 |
|---|---|---|
| 訪客 | 登入、註冊、忘記密碼、補寄驗證信 | 查看私人訂單、火星療癒歷史與管理資料 |
| 未驗證會員 | 補寄驗證信、重新登入 | 下單、送出需要已驗證帳號的操作 |
| 已驗證會員 | 購物、查看自己的訂單與火星療癒歷史 | 查看他人資料、進入管理功能 |
| 管理員 | 依授權範圍查看與管理資料 | 繞過 RLS、直接從前端取得 Service Role Key |
| 發布者 | 在人工放行後部署 | 同時擔任本次程式作者與唯一評審 |

## 6. 建議的單一 Auth 狀態模型

`auth.html` 同一時間只能顯示一種主要狀態：

1. `login`：登入。
2. `signup`：建立帳戶。
3. `verify-email`：等待驗證與補寄驗證信。
4. `forgot-password`：輸入 Email 並寄出重設信。
5. `recovery`：由重設信進入並設定新密碼。
6. `authenticated`：已登入，顯示前往原目的地或會員功能。
7. `error`：連結失效、網路錯誤或服務暫時不可用。

規則：

- 隱藏狀態不得被鍵盤聚焦或被螢幕閱讀器當成目前表單。
- Recovery 狀態不得同時顯示登入／註冊操作。
- 註冊成功但需要 Email 驗證時，必須明確進入 `verify-email` 狀態。
- 已登入使用者開啟 Auth 頁時，不應繼續看到一般登入表單。

## 7. 建議的使用者流程

### 7.1 登入

1. 輸入 Email 與密碼。
2. 前端做基本格式檢查。
3. 呼叫 Supabase `signInWithPassword()`。
4. 成功後確認 Email 是否已驗證。
5. 有安全合法的回跳位置則返回原頁；否則進入會員預設目的地。
6. 管理員若從管理頁進入，登入後應回到原管理頁。

### 7.2 註冊

1. 輸入 Email、密碼、確認密碼。
2. 顯示密碼規則與即時符合狀態。
3. 呼叫 Supabase `signUp()`。
4. 若需要 Email 驗證，顯示已寄信、信箱地址、垃圾郵件提醒及補寄按鈕。
5. 驗證完成後回到安全的原目的地或會員首頁。

### 7.3 忘記密碼

1. 使用獨立的 `forgot-password` 狀態，不依賴登入欄位內已填寫的 Email。
2. 輸入 Email 後寄出重設信。
3. 無論帳號是否存在，對外顯示一致訊息，避免帳號枚舉。
4. 提供返回登入、重新寄送及聯絡管理員指引。

### 7.4 重設密碼

建議只保留 `auth.html` 的 Recovery 流程，廢止重複的獨立正式流程；若保留 `reset-password.html`，則必須反向改成唯一入口，兩者不可同時維護。

Recovery 流程：

1. 驗證 URL 中的 recovery session。
2. 失效時顯示重新申請連結。
3. 輸入新密碼與確認密碼。
4. 更新成功後登出 recovery session。
5. 導回登入狀態，要求使用新密碼重新登入。

### 7.5 登出

- 所有頁面的登出操作使用同一共用函式。
- 登出後清除回跳暫存與敏感 UI 狀態。
- 預設回首頁或登入頁，不保留管理頁畫面。

## 8. 回跳與導向規範

### 單一來源

統一使用 `localStorage.wave_redirect_after_login`，不再同時維護不同的 `?redirect=` 寫法。

### 安全規則

- 只允許同網域 URL。
- 禁止回跳 Auth 頁本身，避免循環。
- 禁止 `javascript:`、外部網域與無法解析的 URL。
- 回跳值只使用一次，登入成功或登出後立即清除。
- 回跳前重新確認目標頁權限；登入不代表一定有管理權限。

### 預設目的地

需要使用者決策：

- 方案 A：登入後回首頁。
- 方案 B：登入後回訂單／會員歷史頁。
- 方案 C：一般會員回會員歷史頁，管理員回管理入口。

## 9. 管理員權限規劃

### 短期方案

- 將管理員 Email 集中在單一共用配置或 helper。
- 所有管理頁使用同一 Auth Guard。
- 未登入：導向 Auth 並保存原頁。
- 已登入但無權限：顯示明確 403 頁面或無權限區塊，不靜默跳首頁。
- 真正資料保護仍由 RLS 負責。

### 中期方案

若管理員可能超過一人，建立 `user_roles` 或 Supabase Custom Claims：

- `super_admin`
- `order_admin`
- `mars_healing_admin`
- `report_viewer`

角色授權必須能對應 RLS，不能只存在前端。

## 10. Supabase 安全核對

實作前先對線上專案進行只讀核對：

### Auth

- Site URL。
- Redirect URLs。
- Email confirmation 是否啟用。
- Password recovery 回跳。
- SMTP 狀態、寄件人與速率限制。
- Session 有效期與 Refresh Token 設定。

### Database

- `profiles` 是否存在 `USING (true)` 的公開讀取政策。
- `orders`、`order_items`、`cart_items`、`favorites`、`mars_healing_registrations` 是否啟用 RLS。
- 線上 Policy 是否與本機 SQL 一致。
- 管理員 Policy 是否仍只依單一 Email。

### Storage

- `mars-healing-photos` 必須為 Private bucket。
- 一般會員只能存取自己的目錄。
- 管理員只依核准角色讀取。
- Signed URL 有效期保持短效。

### P0 個資原則

- 電話、地址、匯款末五碼不可公開讀取。
- 公開個人頁若需要姓名或頭像，應使用公開欄位或專用公開 View，不直接開放完整 `profiles`。

## 11. 介面與體驗規劃

### 視覺方向

延續 WAVE ART MALL 的深色藝術氛圍，但登入頁應比商城頁更安靜、更可信任：

- 主色：深黑與暖金。
- 輔色：低飽和青色只用於次要操作。
- 避免過多發光與動畫干擾輸入。
- 明確區分主要操作、次要操作與說明文字。
- 品牌標題保留，但不壓過登入任務。

### 表單體驗

- 每個 input 都有明確 `label` 與錯誤訊息區。
- 增加顯示／隱藏密碼。
- 增加 Caps Lock 提示。
- 送出中鎖定重複提交。
- 錯誤顯示在對應欄位及頁面摘要，不只依賴 3 秒 Toast。
- 成功訊息保留足夠時間，並提供下一步按鈕。
- 忘記密碼與補寄驗證信分成不同狀態，不堆在登入按鈕下方。

### 手機版

- 觸控按鈕高度至少約 `44px`。
- 鍵盤彈出時表單不被遮住。
- 錯誤訊息不造成畫面劇烈跳動。
- 支援 Email 鍵盤與 Password Manager autofill。
- iOS Safari、Android Chrome 實測。

### 可存取性

- Tab 切換使用適當 ARIA tab 語意，或改為狀態導覽按鈕。
- 焦點在狀態切換後移到新表單標題或第一個欄位。
- 錯誤訊息使用 `aria-live`。
- 顏色對比符合 WCAG AA。
- 鍵盤可完成全部流程。
- 尊重 `prefers-reduced-motion`。

## 12. 錯誤與異常規劃

必須涵蓋：

- Email／密碼錯誤。
- Email 尚未驗證。
- 帳號已存在。
- 驗證信寄送逾時。
- 重設密碼信寄送逾時。
- Recovery 連結失效或已使用。
- 網路斷線與 Supabase 無回應。
- Too many requests／寄信頻率限制。
- 登入成功但回跳頁無權限。
- Session 過期。

錯誤訊息不得洩漏帳號是否存在；Console 也不得記錄密碼、token 或 recovery URL 完整內容。

## 18. 已採用決策

本 Brief 於 2026-09-30 依使用者「現開始執行」指示凍結，後續設計與實作必須遵守下列決策：

1. 密碼重設統一保留在 `auth.html`，`reset-password.html` 不再作為正式入口。
2. 沒有原始回跳頁時，登入成功依角色分流：一般會員前往會員歷史入口，管理員前往管理入口。
3. 未登入進入訂單歷史、火星療癒歷史與管理頁時，統一立即導向登入頁並安全保存原網址。
4. 權限架構預留多人管理角色；第一階段先集中目前管理員判斷，第二階段再導入角色資料模型與對應 RLS。
5. 先進行 Supabase 線上只讀核對；任何 Policy、Auth、Storage 或 SMTP 線上變更都需另行人工確認。
