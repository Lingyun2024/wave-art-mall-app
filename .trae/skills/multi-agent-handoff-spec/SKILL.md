# Multi-Agent / 多人交接規範設計器

把「多 Agent、多人協作」從一堆角色各說各話，變成一條有前置條件、有匯合點的生產線。

## 核心判準（開工前先念一遍）

- 多 Agent 失敗根因是**接口沒設計**，不是角色不夠多。
- **對話負責協調，產物負責事實。**
- 小團隊（1–3 人）預設答案：**不拆**。
- 一個可驗收的三人系統，通常比一個失控的十人專家團更有用。

## 工作流程

### 1. 決定值不值得拆
三條件都成立才拆：①≥2 子任務能獨立進行 ②需不同資料/方法/工具 ③產物間有清楚交接格式。
再問一句：拆開拿到的是「專業分工 / 並行 / 權限隔離 / 獨立評審」哪一樣？**一樣都說不清 → 不拆。**
反例（不要拆）：改郵件、總結 PDF、格式化表格、單檔小重構。
→ 詳細決策表見 [references/handoff-spec.md](references/handoff-spec.md) §1。

### 2. 啟動 Brief
用 [references/handoff-spec.md](references/handoff-spec.md) §8 的模板產出 `briefs/<task>.md`。必含：目標交付、範圍外、風格約束、角色契約、共享目錄、串行/並行/匯合點、人工確認節點、失敗降級、驗收標準。

### 3. 角色契約表
每個角色寫四欄：**輸入 / 輸出 / 禁止動作 / 完成定義**。「禁止動作」至少 1 條，空著視同沒寫。
→ 預填 6 角色表（主理人 / Brief 師 / 設計 / 開發 / 測試 / 獨立評審）見 references §1。

### 4. 共享產物層（單一事實來源）
定義目錄約定 + 凍結機制：brief 經人確認 → 檔首加 `STATUS: FROZEN` + commit；後續修改開新版本檔並通知下游。
下游只讀上游已確認檔，不靠聊天記憶傳關鍵內容。失敗重試只重跑對應環節。
→ 目錄結構與命名見 references §2。

### 5. 執行順序
標出：串行硬依賴（未凍結不能下一步）、可並行區、以及**匯合點三要素（誰先開始 / 等待什麼 / 在哪匯合）**。只寫並行沒有匯合條件 = 一堆拼不起來的半成品。
→ 見 references §3。

### 6. 主理人 = 工作流控制器
一次只有一人當主理人，寫在 `board.md` 頂部。職責：解釋任務、拆子任務、維狀態、分發最小上下文、檢產物、決策、關鍵節點請人拍板、最終驗收。
→ 8 項職責見 references §4。

### 7. 獨立評審 + CI 門禁
作者不得 approve 自己 PR（含 AI 代寫）；評審只評不改；無第二人時用「AI 評審 + 次日自評」。
CI 門禁最低六條（lint / typecheck / test / 覆蓋率 / build / 安全掃描），紅燈不可合併。
→ 規則與閾值見 references §5。

### 8. 權限隔離
開發（人/AI）可讀寫 `out/`、`feat/*`，不可直推 `main`/上線；AI agent 不可改 `docs/briefs/`、CI 配置、碰 production。環境憑證分開存放。
→ 見 references §6。

### 9. 失敗降級
每個關鍵角色一條降級動作。原則：限制失敗傳播範圍、保留可用產物；降級交付必須說明缺少什麼，不把半成品包裝成成果。
→ 降級表見 references §7。

### 10. 七條設計清單（貼 PR 自檢）
1. 判斷值不值得拆 2. 畫產物流 3. 指定角色寫契約 4. 建共享產物層 5. 標串行/並行/匯合點 6. 主理人維狀態+關鍵節點請人確認 7. 每角色有失敗降級與獨立評審。
→ 複本見 references §9。

## 輸出約定
- 預設產出 Markdown 檔（如 `團隊多Agent交接規範.md` 或貼進任務 repo 的 `docs/`）。
- 若用戶要可直接落地的骨架：建 `docs/briefs/`、`docs/design/`、`docs/decisions/`、`docs/board.md`。
- 若用戶要 CI 設定：產出 GitHub Actions / CI 設定檔，門禁對齊 references §5。
